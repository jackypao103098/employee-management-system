## Slide 1 - Employee Management System

### 這頁要讓面試官記住

亮點是：我不是只完成課程 CRUD，而是把它延伸成有 AWS 部署、Flyway migration、CI/CD 和單元測試的 fullstack project。

### 完整講稿

這個專案我想先用一句話定位：它原本是課程的 CRUD 基礎版本，但我後續把它延伸成一個更接近真實工程情境的 fullstack project。除了功能本身，我也補上部署、資料庫版本控管、自動化流程，以及一些安全性和效能/穩定性相關的考量。

我做的重點不是只有新增、查詢、修改、刪除，而是補上幾個比較能代表工程能力的部分：第一，部署到 AWS，讓系統不只本機能跑；第二，用 Flyway 管理 database migration，讓資料庫變更可以追蹤；第三，用 GitHub Actions 做 CI/CD，讓測試和部署流程自動化；第四，用單元測試保護 service 邏輯，避免之後重構時把原本行為改壞。

另外，安全性和效能我也有放進考量。安全性上，專案有 JWT 安全機制雛形、密碼加密處理，以及敏感設定不進版本控制，而是透過環境變數提供。效能和穩定性上，前端透過 CloudFront 做 CDN，圖片放 S3，資料庫交給 RDS 管理，讓系統責任切分更清楚，也比較容易維護。

技術上，後端使用 Java 17 和 Spring Boot 3.4，前端使用 React 和 TypeScript，資料庫是 PostgreSQL，部署在 AWS 上。Spring Boot 幫我處理 API、分層架構和 security；TypeScript 幫我在 build 前抓型別錯誤；PostgreSQL 負責結構化資料；AWS 則讓系統可以用比較接近真實環境的方式運行。

所以如果要看這個專案的亮點，我會說它不是功能多複雜，而是我有把一個課程專案往「可部署、可測試、可維護」的方向推進。

接下來我先說明專案背景，哪些是課程基礎版本，哪些是我後續自己延伸的部分。

是，CRUD 和安全機制雛形的基礎版本來自課程。但我後續自己做了 domain migration、AWS deployment、CI/CD、多環境設定、production issue fixes、Spring Boot upgrade 和 TypeScript migration。這些才是我想展示的工程能力。

## Slide 3 - AWS Deployment Architecture

### 這頁要讓面試官記住

我理解前端、後端、資料庫和檔案儲存在雲端環境中的責任切分。

### 完整講稿

這頁是系統部署到 AWS 後的整體架構，採用前後端分離。

前端是 React SPA，部署在 AWS Amplify，並透過 CloudFront 提供 CDN。可以把 Amplify 理解成 AWS 上部署前端網站的服務，CloudFront 則讓靜態資源載入更穩定。

後端 Spring Boot 會打包成 Docker container，部署在 Elastic Beanstalk。Elastic Beanstalk 可以理解成 AWS 的應用程式部署平台，它會幫我處理 EC2、load balancer、deployment environment 和 health check，比我手動管理 EC2 更適合這個專案。

資料庫使用 RDS PostgreSQL，因為 RDS 是 managed database service，可以減少自己維護 database server 的成本。員工圖片則放在 S3，因為圖片是檔案，不適合直接塞進 PostgreSQL；資料庫只需要存圖片 key 或 URL。

這樣切分後，前端 hosting、後端 API、資料庫 schema、圖片儲存都有清楚責任。部署或除錯時，也比較容易判斷問題在哪一層。

### 轉場

AWS 架構說完後，下一個重點是資料庫 schema 如何演進。

### 追問補充

如果面試官問：「S3Service 為什麼要封裝？」

可以回答：

我不希望上層 business service 直接依賴 AWS SDK。透過 S3Service 封裝後，上層只需要知道 upload 或 delete image，不需要知道 SDK client、bucket name 或 request 怎麼組。

## Slide 4 - Database Migration with Flyway

### 這頁要讓面試官記住

我理解 database migration 要考慮版本控管、既有資料和 production 風險。

### 完整講稿

資料庫 migration 是這個專案最值得講的技術點。Migration 可以理解成「用版本化 SQL 檔案管理資料庫結構變更」。

我使用 Flyway 管理 schema changes。它會把每一次資料庫變更記錄成版本，例如 V1、V2、V3，並按照順序執行。這解決的是手動改 DB 容易造成環境不一致的問題。否則 local、UAT、production 很可能 schema 不同，也很難追蹤某個欄位是什麼時候加的。

其中一個例子是 Customer 到 Employee 的 domain migration。這不只是 Java class 改名，也包含 table、sequence 和 naming 的調整。我透過 migration scripts 記錄這些變更，讓資料庫演進可以被追蹤。

JPA 設定上，我使用 `ddl-auto: validate`。意思是 Spring Boot 啟動時只檢查 Entity 和 database schema 是否一致，不自動修改 database。這樣可以避免 production schema 在沒有 review SQL 的情況下被 ORM 靜默改掉。

我印象最深的是 NOT NULL migration。本機空資料庫可以直接加 `NOT NULL` 欄位，但 production table 已經有資料，直接加就會失敗。比較安全的流程是：先 nullable 加欄位，再補既有資料，最後才加 `NOT NULL` constraint。這讓我學到 migration 要考慮 production data state，不是只看本機能不能跑。

### 轉場

有了 migration 之後，下一步是讓測試、打包和部署流程可以穩定重複。

### 追問補充

如果面試官問：「為什麼不用 Hibernate 自動建表？」

可以回答：

Hibernate 自動建表在 local 很方便，但 production schema 需要可控、可 review、可追蹤。Flyway 負責改 schema，`ddl-auto: validate` 只負責驗證一致性，風險比較低。

## Slide 5 - CI/CD & Multi-env Deployment

### 這頁要讓面試官記住

我不是只會手動部署，而是能把測試、打包、部署和環境設定整理成可重複流程。

### 完整講稿

這頁把 CI/CD 和多環境設定放在一起講，因為它們共同解決「怎麼穩定交付」的問題。

CI 可以理解成每次程式碼變更後，自動跑測試和檢查。CD 則是把通過檢查的版本自動打包和部署。我使用 GitHub Actions，因為它和 GitHub repo 整合很直接，可以在 push 或 PR 時自動觸發流程。

CD 部分，我使用 Google Jib Maven Plugin 建 Docker image。Docker image 可以理解成把應用程式和執行環境包成一個可部署的包。Jib 的好處是可以直接從 Maven build 出 image，不一定需要自己手寫完整 Dockerfile。

多環境設定上，我盡量讓 source code 保持 environment-neutral。local、UAT、AWS 需要不同 datasource、S3 bucket 或 credentials，但這些不應該寫死在程式碼裡，而是透過 Spring profiles 和 environment variables 提供。

這樣做的目的，是讓每次測試、打包、部署都走同一套流程，減少手動操作造成的環境差異，也讓部署紀錄比較容易追蹤。

### 轉場

最後我會講這個專案如何做單元測試，說明我如何驗證 service 邏輯。

### 追問補充

如果面試官問：「CI 裡為什麼要跑測試？」

可以回答：

因為 CI 的價值是讓每次 push 或 PR 都有基本品質檢查，不要只靠本機測過。即使是單元測試，也可以提早抓到 service logic、例外處理或 refactor 造成的 regression。

## Slide 6 - Unit Testing Strategy

### 這頁要讓面試官記住

我有用單元測試驗證 service 邏輯、例外情境和外部依賴互動。

### 完整講稿

最後這頁是單元測試。單元測試可以理解成「針對一小段程式邏輯做自動化驗證」。它解決的問題是：功能現在看起來能跑，但之後重構或修改時，不知道有沒有把原本行為改壞。

這個專案的後端是分層架構，所以我主要測 service layer。因為很多 business rules 都在 service 裡，例如新增員工時要檢查 email 是否重複、查不到員工時要丟 `ResourceNotFoundException`、更新資料時要判斷是否真的有變更。

以 `EmployeeServiceTest` 為例，我用 Mockito mock `EmployeeDao`、`PasswordEncoder`、`S3Service`。Mockito 是 Java 常用的 mock 工具，可以假裝某個 dependency 回傳指定結果。這樣做的原因是，我想專注測 service 本身，不希望測試被 database 連線或 AWS SDK 影響。

我會測 happy path，例如 email 沒有重複時，可以成功新增員工；也會測 failure path，例如 email 重複要丟 `DuplicateResourceException`，找不到員工要丟 `ResourceNotFoundException`，更新沒有變更要丟 `RequestValidationException`。

除了 service，我也有測比較容易出錯的小元件。例如 `EmployeeRowMapperTest` 驗證 JDBC mapping 是否正確，`S3ServiceTest` 確認 upload / download 時 bucket、key 和 request 有沒有組對。

總結來說，單元測試的價值不是只看 coverage，而是把容易壞的判斷邏輯固定下來。之後如果我重構 service 或換 DAO implementation，測試可以提早提醒我是不是破壞了原本行為。

### 收尾

總結來說，這個專案讓我練到的不只是 Spring Boot CRUD，而是從 service 單元測試、database migration、CI/CD 到 AWS deployment 這一整段工程流程。

### 追問補充

如果面試官問：「為什麼要 mock DAO？」

可以回答：

因為這一層測的是 service 邏輯，不是 database 本身。把 DAO mock 起來後，我可以控制它回傳 email exists、employee exists 或找不到資料，然後驗證 service 是否做出正確判斷。

如果面試官問前端 TypeScript：

可以回答：

我把前端 build 改成 `tsc && vite build`，讓 type checking 成為 build gate。TypeScript migration 時抓到一個 axios headers 設定錯誤，這讓我覺得 TypeScript 不是形式上的加分，而是真的能提早抓到 bug。
